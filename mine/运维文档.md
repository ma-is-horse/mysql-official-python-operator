# MySQL InnoDB Cluster 故障恢复总结

## 1. 故障概况

- 集群名称：`mcamel-common-mgr-cluster`
- MySQL Server：`8.0.37`
- Group Replication 通信栈：`MYSQL`
- InnoDB Cluster metadata：`2.1.0`
- 集群拓扑：3 节点、Single-Primary
- 节点：
  - `mcamel-common-mgr-cluster-0`
  - `mcamel-common-mgr-cluster-1`
  - `mcamel-common-mgr-cluster-2`

故障期间，`cluster-0` 和 `cluster-1` 仍为 `ONLINE/SECONDARY`，但原 PRIMARY `cluster-2` 的 Group Replication 已停止。集群保有 2/3 quorum，却没有可写 PRIMARY，最终状态为：

```text
status: OK_NO_TOLERANCE_PARTIAL
cluster-0: ONLINE / SECONDARY / R/O
cluster-1: ONLINE / SECONDARY / R/O
cluster-2: OFFLINE/UNREACHABLE / PRIMARY
```

这是一种异常的“多数派仍在线，但 PRIMARY 身份滞留在离线节点”状态，导致拓扑管理和写流量均不可用。

## 2. 主要故障现象

### 2.1 无法直接取得集群对象

连接到 Group Replication 未运行的节点时，执行：

```javascript
dba.getCluster()
```

出现：

```text
This function is not available through a session to a standalone instance
(metadata exists, instance belongs to that metadata, but GR is not active)
```

原因是当前 MySQL Shell 会话连接到了 GR 未激活的实例，而不是健康的在线成员。

### 2.2 `rejoinInstance()` 失败

```javascript
cluster.rejoinInstance("...cluster-2...:3306")
```

出现：

```text
No PRIMARY member found for cluster
Cluster metadata not found
```

`rejoinInstance()` 属于拓扑变更，需要可用 PRIMARY。此时集群虽然有 quorum，但没有在线 PRIMARY，因此 rejoin 不是第一步。

### 2.3 手工启动 Group Replication 失败

在 `cluster-2` 执行：

```sql
START GROUP_REPLICATION;
```

日志出现：

```text
Timeout on wait for view after joining group
The member was unable to join the group
Error connecting to all peers
```

这表示节点能够发起连接，但无法正常进入新的 Group Replication 视图。反复执行 `START GROUP_REPLICATION` 不能解决 PRIMARY/视图异常。

### 2.4 强制 quorum 被拒绝

```javascript
cluster.forceQuorumUsingPartitionOf(...)
```

出现：

```text
Cannot perform operation on a healthy cluster because it can only be used
to restore a cluster from quorum loss.
```

说明 `cluster-0/1` 已组成多数派，集群并未丢失 quorum，因此不能使用该命令。

### 2.5 手工指定 PRIMARY 被拒绝

```sql
SELECT group_replication_set_as_primary('<cluster-0-server-uuid>', 300);
```

出现：

```text
All members in the group must be reachable.
```

原因是原 PRIMARY `cluster-2` 仍残留在成员视图中，但处于不可达状态。

### 2.6 强制收缩成员视图被拒绝

```sql
SET GLOBAL group_replication_force_members = '<cluster-0>,<cluster-1>';
```

出现：

```text
group_replication_force_members can only be updated when Group Replication
is running and majority of the members are unreachable.
```

当前不可达成员只有 1/3，仍存在多数派，因此 MySQL 不允许使用该变量。

## 3. 最终采用的恢复方案

由于以下条件同时存在：

- 集群拥有 quorum，不能强制 quorum；
- 离线 PRIMARY 阻止正常切主；
- 所有成员并非全部可达，不能手工指定 PRIMARY；
- 不满足 `group_replication_force_members` 的使用条件；
- 在线的两个 SECONDARY 无法提供写服务；

最终采用了**受控停止所有 Group Replication，然后按完整停机流程重启 InnoDB Cluster**。

### 3.1 隔离写流量

恢复期间暂停应用写入，并确保所有节点只读：

```sql
SET GLOBAL super_read_only = ON;
```

### 3.2 停止所有节点的 Group Replication

按 `cluster-2`、`cluster-1`、`cluster-0` 的顺序执行，最后停止选定的恢复节点：

```sql
STOP GROUP_REPLICATION;
```

如果某节点的 GR 本来就未运行，相应报错可以忽略。

### 3.3 明确连接数据最新的节点

本次根据 GTID/status 信息选择 `cluster-0`。管理操作必须连接具体 Pod，不应连接可能把会话分配到不同后端的负载均衡 Service。

```javascript
\connect --mysql mysqladmin@mcamel-common-mgr-cluster-0.mcamel-common-mgr-cluster-instances.mcamel-system.svc.cluster.local:3306
\js
```

### 3.4 先进行 dry run

```javascript
dba.rebootClusterFromCompleteOutage(
  "mcamel-common-mgr-cluster",
  {
    primary: "mcamel-common-mgr-cluster-0.mcamel-common-mgr-cluster-instances.mcamel-system.svc.cluster.local:3306",
    dryRun: true
  }
);
```

执行正式恢复前确认：

- 所选 seed/primary 是 `cluster-0`；
- 所选节点具有 GTID superset；
- 没有 GTID divergence 或数据丢失警告；
- 所有成员的 GR 均已停止。

### 3.5 正式恢复

```javascript
var cluster = dba.rebootClusterFromCompleteOutage(
  "mcamel-common-mgr-cluster",
  {
    primary: "mcamel-common-mgr-cluster-0.mcamel-common-mgr-cluster-instances.mcamel-system.svc.cluster.local:3306"
  }
);
```

如果某个离线副本不可达，且已确认 `cluster-0` 是 GTID 最新节点，才考虑：

```javascript
var cluster = dba.rebootClusterFromCompleteOutage(
  "mcamel-common-mgr-cluster",
  {
    primary: "mcamel-common-mgr-cluster-0.mcamel-common-mgr-cluster-instances.mcamel-system.svc.cluster.local:3306",
    force: true
  }
);
```

`force: true` 可能丢弃未包含在所选节点 GTID 集合中的事务，不能跳过 GTID 检查直接使用。

### 3.6 恢复后检查与修复

```javascript
cluster.status({extended: 2});
cluster.rescan();
```

如果某个副本没有被自动恢复，再执行：

```javascript
cluster.rejoinInstance(
  "mysqladmin@mcamel-common-mgr-cluster-2.mcamel-common-mgr-cluster-instances.mcamel-system.svc.cluster.local:3306"
);
```

只有确认副本数据可以完全覆盖、增量恢复不可用时，才使用 Clone：

```javascript
cluster.rejoinInstance(
  "mysqladmin@mcamel-common-mgr-cluster-2.mcamel-common-mgr-cluster-instances.mcamel-system.svc.cluster.local:3306",
  {recoveryMethod: "clone"}
);
```

Clone 会覆盖目标副本的现有数据。

## 4. 恢复完成的验收标准

执行：

```javascript
cluster.status({extended: 2});
```

应确认：

- 集群状态为 `OK`，或节点恢复过程中暂时为合理的 `OK_PARTIAL`；
- 一个节点为 `ONLINE / PRIMARY / R/W`；
- 另外两个节点最终为 `ONLINE / SECONDARY / R/O`；
- `inApplierQueueCount` 和 `inQueueCount` 最终归零；
- 没有 recovery account、metadata、GTID divergence 等告警；
- MySQL Router 的读写端口能够路由到新 PRIMARY；
- 应用读写和关键业务校验通过。

可使用 SQL 再次确认：

```sql
SELECT MEMBER_ID, MEMBER_HOST, MEMBER_PORT, MEMBER_STATE, MEMBER_ROLE
FROM performance_schema.replication_group_members;
```

## 5. 经验与注意事项

1. **必须连接明确的实例。** 故障处理期间不要通过普通负载均衡 Service 运行 AdminAPI，否则不同命令可能落到不同 Pod。
2. **先识别故障类型。** `NO_QUORUM` 才适合 `forceQuorumUsingPartitionOf()`；全部 GR 停止才适合 `rebootClusterFromCompleteOutage()`。
3. **不要看到 OFFLINE 就直接 rejoin。** `rejoinInstance()` 依赖健康 PRIMARY；应先修复 quorum 和 PRIMARY。
4. **不要反复手工执行 `START GROUP_REPLICATION`。** 应同时检查在线节点日志、成员视图和 GTID 状态。
5. **`force` 必须最后使用。** 无论强制 quorum、强制成员视图还是强制完整停机恢复，都存在脑裂或事务丢失风险。
6. **先 dry run。** 完整停机恢复前必须验证 GTID superset 和候选 PRIMARY。
7. **升级 metadata。** 集群完全稳定后，在维护窗口执行：

   ```javascript
   dba.upgradeMetadata();
   ```

8. **轮换已暴露密码。** 本次排障过程中密码曾以明文进入终端历史/截图，应更新数据库账号密码及对应 Kubernetes Secret，并清理可访问的命令历史和截图。

## 6. 建议的后续改进

- 检查 MySQL Router 和 Kubernetes Service，确保管理连接与业务连接分离。
- 为每个 Pod 保留可直接连接的管理入口，避免排障期间命令漂移到其他实例。
- 监控以下状态：PRIMARY 缺失、`UNREACHABLE`、`OFFLINE`、`NO_QUORUM`、复制队列堆积。
- 收集并集中保存三个节点的 MySQL error log，确保可以按同一时间窗口关联分析。
- 检查 `group_replication_member_expel_timeout`、自动 rejoin 和退出动作配置是否符合故障恢复目标。
- 定期演练 `dryRun`、完整停机恢复、节点 rejoin 和 Clone 恢复流程。
- 在 metadata 升级前确认 MySQL Shell 与 MySQL Server 的版本兼容性。
